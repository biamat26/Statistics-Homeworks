Private Key → Public Key

Elliptic-curve scalar multiplication as a one-way function — the mechanism behind Ethereum keys (secp256k1), shown on a toy curve.

1. The idea

In Ethereum a private key is a secret integer k and the public key is a point Q of an elliptic curve obtained by scalar multiplication of a fixed, public base point G:

Q = k · G = G + G + … + G  (k times)

Computing Q from k is fast (about log₂k point operations with double-and-add), while recovering k from Q is the Elliptic Curve Discrete Logarithm Problem (ECDLP), believed to be infeasible on a curve with ~2²⁵⁶ points. This makes k ↦ kG a one-way function.

Ethereum uses secp256k1: y² = x³ + 7 over a 256-bit prime field. To see every step we use the same equation over a tiny field:

E : y² ≡ x³ + 7 (mod 17),   G = (1, 5),   k = 6

3. Computation

3.1 Repeated addition: G, 2G, 3G, …, kG

Point addition: slope λ = (y₂ − y₁)/(x₂ − x₁) for two different points, λ = (3x₁² + a)/(2y₁) for doubling; then x₃ = λ² − x₁ − x₂, y₃ = λ(x₁ − x₃) − y₁, everything mod p (division = multiplication by the modular inverse).

3.2 Faster: double-and-add

Read the bits of k from left to right: always double, and also add G when the bit is 1. It needs about log₂k doublings instead of k − 1 additions.

7. Discussion: one-way function vs. hash function

What the experiments show

  • Output distribution. Since k ↦ kG is a bijection between {0,…,n−1} and the subgroup ⟨G⟩, a uniform k gives a perfectly uniform point. But the coordinates are not uniform over {0,…,p−1}: only about half of the x values can occur (those with x³ + 7 a square), and each occurs exactly twice per period, because kG and −kG = (n−k)G share x. A χ² test against the uniform distribution therefore rejects uniformity of x. On the p = 211 curve even y is restricted: only 66 values occur, each 3 times. The reason is that p ≡ 1 (mod 3), so there is a cube root of unity β with β³ = 1, and (x, y) ↦ (βx, y) maps the curve to itself: three points share every y. secp256k1 has the same property (it is the “GLV endomorphism” used to speed up the computation). On the toy curve (p = 17 ≢ 1 mod 3) this does not happen, and with a generator of the whole curve y is perfectly uniform.
  • Bits. The top bit is biased simply because values stop at p − 1 < 2L (range effect). For secp256k1, p is so close to 2²⁵⁶ that this bias is invisible (≈ 2⁻²²⁴).
  • Correlation. Pearson's r(k, x) is exactly 0 — not because input and output are independent, but because of the symmetry x(kG) = x((n−k)G). Zero linear correlation does not mean independence: the map is deterministic and highly structured.
  • Avalanche. Flipping one bit of k changes about half of the output bits, so the output looks unpredictable. But the change is fully predictable inside the group: f(k ⊕ 2i) = f(k) ± 2iG.
  • Algebraic structure. (a + b)G = aG + bG holds for every a, b (checked numerically above). For a hash function such a relation would be a catastrophic break; for public-key cryptography it is exactly what makes signatures (ECDSA) and key exchange (ECDH) possible.
  • Small toy curve. With G = (1, 5) the order is 9: there are only 9 public keys and anyone can invert the function by trying them all. Statistics can look fine while the function is trivially invertible.

Conclusion

Uniformity, absence of correlation, avalanche behaviour and absence of algebraic relations are the properties expected from cryptographic hash functions (random-oracle-like behaviour). Elliptic-curve scalar multiplication shares only some of them and deliberately keeps an algebraic structure. Its security does not come from statistical properties but from the computational hardness of the ECDLP on a group of huge prime order: good-looking statistics are a sanity check, never a proof of one-wayness.
