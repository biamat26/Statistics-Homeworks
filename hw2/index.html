From Wallet Seed to Ethereum Address

Hashing, key derivation and cryptographic primitives in the Ethereum wallet pipeline — computed live in your browser, step by step, with a statistical look at every stage.

1. The pipeline at a glance

A modern Ethereum wallet (MetaMask, Rabby, Exodus, Rainbow, …) stores one secret only: a list of 12–24 words. Every private key, public key and address of the wallet is derived from those words by a chain of standards, each built on a different cryptographic primitive:

  1. Entropykey generation 128–256 random bits from a CSPRNG — the only random step
  2. ↓ BIP-39 words + SHA-256 checksum
  3. Mnemonicencodingchecksum the entropy written as words from a 2048-word list
  4. ↓ BIP-39 PBKDF2-HMAC-SHA512, 2048 iterations
  5. Seed (512 bits)key derivation key stretching, optional passphrase
  6. ↓ BIP-32 / BIP-44 HMAC-SHA512 tree, path m/44'/60'/0'/0/i
  7. Private key kkey derivation a 256-bit integer, one per account
  8. ↓ secp256k1 Q = k·G
  9. Public key Qpublic-key crypto a curve point (x, y), 64 bytes
  10. ↓ Keccak-256, keep the last 20 bytes
  11. Addresshashingencoding (hex) 160 bits, 40 hex characters
  12. ↓ EIP-55 upper/lower case from Keccak-256 of the address
  13. Checksummed addresschecksumencoding same address, with error detection

4. SHA-2, SHA-3 and Keccak

Both families are cryptographic hash functions, but they are built in completely different ways. SHA-2 (SHA-256, SHA-512, 2001) uses the Merkle–Damgård construction: a compression function is applied block by block to a chaining value. Keccak uses the sponge construction: the message is absorbed into a large 1600-bit state that is mixed by a fixed permutation (Keccak-f), and the digest is then squeezed out. Keccak won the NIST SHA-3 competition in 2012 and was standardized as SHA-3 in FIPS 202 (2015), as an alternative to SHA-2 rather than a replacement.

During standardization NIST changed the padding: SHA3-256 appends the domain-separation bits 01 before the usual 10…01 padding (first padding byte 0x06), while the original Keccak submission starts with 0x01. Ethereum had already adopted Keccak before FIPS 202 was published and kept the original rule, so Keccak-256 ≠ SHA3-256: same permutation, same rate and capacity, different output.

5. Historical context

The wallet standards are recent, but they are built on primitives that are decades older: each layer reuses well-studied building blocks.

  1. 1976–77Diffie–Hellman key exchange (1976) and RSA (1977): public-key cryptography is born.
  2. 1985Elliptic-curve cryptography proposed independently by Koblitz and Miller: same security as RSA with much shorter keys.
  3. 1996–97HMAC (Bellare, Canetti, Krawczyk; RFC 2104): a keyed hash built from any hash function.
  4. 2000PBKDF2 (RFC 2898) for password-based key derivation; SEC 2 publishes the parameters of secp256k1.
  5. 2001SHA-2 family (SHA-256, SHA-512) published by NIST.
  6. 2007–12NIST SHA-3 competition; Keccak wins in October 2012.
  7. 2009Bitcoin launches, using secp256k1 and SHA-256.
  8. 2012BIP-32: hierarchical deterministic wallets (one seed → a tree of keys).
  9. 2013BIP-39: mnemonic sentences to back up the seed with words.
  10. 2014BIP-44: a standard path structure, so that different wallets find the same accounts.
  11. 2015SHA-3 standardized (FIPS 202, August) with the new padding. Ethereum launches (July) with the original Keccak-256.
  12. 2016EIP-55: mixed-case checksum for Ethereum addresses.

6. Why so many techniques instead of one algorithm?

Because each step has a different job and therefore needs a different property. No single primitive provides all of them, and the ones that could in principle be stretched to do so would be the wrong tool: a hash cannot produce signatures, a signature scheme cannot compress, and a checksum is useless against an attacker.

LayerPurposeProperty it needsWhy not something else
BIP-39 / BIP-32 / BIP-44
key management & derivation		 Back up one human-readable secret and regenerate any number of keys from it, in the same order in every wallet. Determinism, one-wayness, independence of sibling keys, human-friendly encoding, a common path convention. Storing many random keys would require a new backup for every account; a hash alone does not give a tree with hardened/non-hardened branches or a shared path standard.
secp256k1
public-key crypto		 Prove ownership: sign transactions with k, let everyone verify with Q. A trapdoor relation with algebraic structure (Q = kG) that supports ECDSA signatures. A hash is one-way but has no structure: H(k) cannot verify a signature. RSA would work but needs much larger keys and signatures.
Keccak-256
hashing		 Turn a 64-byte public key into a short, uniform 20-byte identifier. Compression, collision resistance, random-looking output; it also hides Q until the first transaction. Truncating Q directly would keep its structure (x and y are linked by the curve equation); a checksum is not collision resistant.
EIP-55
checksum / error detection		 Catch typos when an address is copied by hand. Cheap, backward compatible (case-insensitive hex stays valid), high detection rate. Adding extra characters would change the address format; a cryptographic signature would be overkill for accidental errors.

The design is modular: each layer can be analysed, tested and replaced on its own. The same BIP-39 seed and BIP-32 tree serve Bitcoin (coin type 0), Ethereum (coin type 60) and hundreds of other chains; only the last steps (curve, hash, address format) change.

7. Statistical properties

We now treat each stage as a black box and look at its outputs with the same tests used in Homework 1: frequencies, χ² goodness of fit, bit balance, correlation and avalanche. The experiments use fresh random data each time you press Run.

What the numbers say

  • Hash outputs look uniform and independent. Every bit of Keccak-256 is 1 about half of the time (A), byte values pass the χ² test (B), and flipping a single input bit changes about 128 output bits with the binomial spread of a fair coin (C). Even highly structured inputs such as 0, 1, 2, … produce outputs with no correlation to the input (D). This is the random-oracle-like behaviour expected from a hash function.
  • The whole pipeline inherits it. Addresses use the 16 hex digits uniformly (E) and a one-bit change of the private key changes about half of the 160 address bits (F). Compare with Homework 1: k ↦ kG alone keeps an algebraic structure, but after Keccak-256 that structure is no longer visible in the address.
  • Derived keys are statistically independent. Consecutive BIP-32 children differ in about 128 of 256 bits (G): knowing account i says nothing about account i + 1 (unless the parent extended public key leaks together with a non-hardened child private key).
  • Checksums trade bits for error detection. A BIP-39 phrase of 12 random words is valid only with probability 2⁻⁴ = 1/16, because the last 4 bits are a SHA-256 checksum. An EIP-55 address has on average 40 · 6/16 = 15 letters (H), each carrying one check bit; a random typo goes undetected with probability E[2⁻ᴸ] = (13/16)⁴⁰ ≈ 0.0245%. The experiment also reveals a subtler weakness: with the same probability an address has all its letters in lowercase (or all in uppercase), so it looks exactly like an address without checksum and wallets accept it with any typo. EIP-55 is cheap and backward compatible, and this is the price.
  • Statistics cannot measure entropy. A seed from 128 random bits and a seed from a weak source (a short password, a bad random number generator, the integers of experiment D) produce outputs that look equally uniform, because the hash and derivation functions hide the input. The security of the whole wallet rests on the generation step: 128 truly random bits. All later steps are deterministic and add no entropy.

8. What to look for in real wallet software

  • Creating a wallet (MetaMask, Rabby, Exodus, Rainbow): the app generates the entropy and shows the 12 words — key generation and BIP-39 encoding. The “confirm your phrase” screen and the error shown for a wrong last word are the BIP-39 checksum at work.
  • Importing the test phrase test test … junk shows account 0xf39Fd6e51aad88F6F4ce6aB8827279cffFb92266: the same result as section 2, because every wallet implements the same standards.
  • “Add account” derives the next index i on m/44'/60'/0'/0/i (BIP-44). Removing the wallet and re-importing the words brings back exactly the same accounts: nothing but the seed needs to be backed up.
  • Different wallets, different paths: some wallets (for example Ledger Live) increase the account level (m/44'/60'/i'/0/0) instead of the index, so the same words can show different addresses in different apps. Multi-chain wallets such as Exodus use the same seed with different coin types (0 for Bitcoin, 60 for Ethereum).
  • Importing a single private key skips BIP-39/32/44 entirely: that account cannot be recovered from the seed phrase.
  • Addresses are displayed in EIP-55 mixed case; wallets reject or warn about an address whose case pattern does not match the checksum.
